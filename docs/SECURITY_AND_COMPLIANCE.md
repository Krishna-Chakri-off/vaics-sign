# Security & compliance
- **AuthN/AuthZ**: requester screens use the CMS JWT login. Senders: roles admin, change_manager, implementer, requester. Documents scoped to organization; non-admins see only their own; enforced server-side (tests for 401/403).
- **Signing links**: 256-bit random token, only SHA-256 stored; valid only for the *current* signer in order; expires (7 days); revoked after signing, decline, cancel, or reissue.
- **Access code** (second factor, separate email): 6–8 digits from `secrets`, stored as HMAC-SHA256(SECRET_KEY, recipient id + code); expires (72 h); 5 wrong attempts → lockout (reissue by sender only); successful unlock issues a 30-minute session token (hash stored) required for viewing the PDF, signing and declining. Note: link and code going to the same mailbox protect against link forwarding/leakage, not against mailbox compromise.
- **Dev outbox**: when SMTP is not configured the code is stored in plaintext in `sign_emails` so the demo can proceed. Never run production without SMTP; with SMTP configured codes are never stored or displayed.
- **Document privacy**: random file names in SIGN_STORAGE_DIR, served only through authorised endpoints / valid session; `Cache-Control: no-store`. Not encrypted at rest (gap).
- **Integrity**: original SHA-256 on upload; per-field SHA-256 over version hash + signer + time + reason; rolling version hash; final PDF SHA-256; hash-chained audit log with UTC time, IP, user agent. The final PDF is not PAdES/cryptographically sealed (gap); the audit log is append-only by application, not WORM-stored.
- **Secrets**: none in code; `.env.example` contains placeholders only. Change SECRET_KEY. SES SMTP credentials go in `.env` / a secret manager.
- **Gaps**: no rate limiting per IP, no encryption at rest, no Alembic migration, no virus scan of uploads, no data-retention job.
- **Legal**: this is an **electronic signature** (typed name-generated signature + email access code + consent + audit trail). It is **not** a certificate-backed digital signature (DSC) or **Aadhaar eSign** under the Information Technology Act, 2000 (s.3A / Second Schedule). Documents in the First Schedule of the IT Act (e.g. negotiable instruments other than cheques, powers of attorney, trusts, wills, contracts for sale of immovable property) cannot be validly executed this way. eSign/DSC via a licensed ESP is only an integration boundary — not implemented. Obtain legal review before production use.
